# Monitoring and recovery handoff

Prepared read-only hook: set CENTERLY_MONITOR_WEB_ORIGIN to the approved HTTPS hostname and run `node scripts/pilot-health.mjs`. JSON contains only check name, pass/fail, HTTP status and elapsed milliseconds; exit 1 signals failure. It sends no Auth headers, cookies, PII or messages. Mocked tests cover shell, HTTP error, network failure and unsafe origin. It has not been scheduled or pointed at production. It verifies the web shell only, not authenticated RPC health.

After owner approves a target/recipient, operator schedules every five minutes on trusted infrastructure; alert after two consecutive failures, recovery after two passes. Keep detailed logs private with seven-day proposed retention. Verify actual alert delivery with a controlled outage before launch. Daily provider dashboard review: Auth/RPC error rate and p95 latency, database/egress/storage utilization, backup freshness (<24h target), denied-access/conflict spikes, crash/ANR reports and financial reconciliation exceptions. Alert thresholds proposed: error rate >1% for ten minutes, p95 >2s for ten minutes, capacity >80%, missed backup. Calibrate to pilot traffic; do not collect SQL bodies, payloads, contact data or session tokens. Flutter observer already logs event/type names without values; no external crash SDK is enabled. Crash collection destination/consent remains an owner configuration gate.

Recovery drill sequence (not executed against hosted services):

1. Operator inventories source revision, public configuration fingerprint, migration history/hash manifest, private service/Auth settings, storage bucket/object inventory and signing-key custody. Verify recoverable backup timestamps and encrypted offsite copy. Never commit credentials or dumps.
2. With explicit approval, create isolated matching-version restore target, outbound mail disabled. Restore provider database backup/export with documented roles/grants/Auth support; copy Storage objects separately and restore service configuration using provider-supported steps. No customer invitations or password resets during drill.
3. Compare table counts and full catalog/RLS/grants, immutable payment/reversal/audit/attendance history, exact decimal totals and two-tenant denial. Verify Auth login/restore/logout and Storage access with approved drill identities. Do not redirect production clients or reuse SEC27 mutation scripts.
4. Record backup ID, latest committed transaction time, restore start/end, measured lost interval and time-to-usable service. Target RPO <=24h / RTO <=4h remains unproven until this succeeds. Owner signs recovery report and target disposal/retention separately.
5. Incident rollback uses previous compatible immutable clients; database repair is an approved additive forward fix. Any restore requires an explicit reconciliation/data-loss plan and authorization. Preserve financial/attendance/audit history throughout.

Existing isolated PGlite snapshot restore is development evidence only. Provider DB/Auth/Storage recovery, scheduled monitoring and alert delivery are unavailable pending an approved environment/operator. Detailed incident and onboarding procedures remain in PILOT_OPERATIONS.md.
